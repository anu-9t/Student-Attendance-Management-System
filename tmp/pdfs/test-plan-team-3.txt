1. Introduction
Purpose
This document is the Software Test Plan (STP) for the Student Attendance Management System (SAMS), prepared 
by Team 3 for the UE24CS341A Software Engineering mini-project. It defines objectives, scope, strategy, 
resources, schedule, and responsibilities for testing SAMS against the requirements and use cases defined in the 
Phase-1 SRS (v1.0).
This document is being finalised ahead of the Phase-2 Project Plan, on the course coordinator's instruction, since 
test design can proceed directly from the approved SRS and use-case model without waiting on the 
WBS/scheduling artifacts that Phase-2 covers.
Scope
Testing covers all seven use cases defined in Section 7 of the SRS (UC-01 through UC-07), which together 
implement the 20 functional requirements (SAM-F-001 to SAM-F-020) and 5 security requirements (SAM-SEC-001 
to SAM-SEC-005). Excluded from this phase: the Django/MySQL framework internals themselves, and full-scale 
performance/load testing (see Sections 3 and 4).

• Software Requirements Specification, Student Attendance Management System, v1.0, Team 3, 03-09-2026 — 
in particular its Requirements Traceability Matrix (Section 8), which this plan builds on rather than repeats 
(see Section 13).

structure, including the lighter, example-based treatment of Section 13.
• Django Documentation, https://docs.djangoproject.com/ — framework-specific test tooling (e.g. Django's 
TestCase class).

• Subject Module (subject creation, faculty assignment) — SAM-F-008, SAM-F-009

• Calculation Module (attendance percentage) — SAM-F-015

• Access Control Module (role enforcement, data isolation) — SAM-SEC-001, SAM-SEC-002, SAM-SEC-004
• Audit Module (logging of administrative actions) — SAM-SEC-005

4. Features Not to be Tested
• Django's own authentication internals (session handling, password hashing algorithm correctness) — the 
project relies on Django's built-in, well-tested implementation rather than re-testing the framework itself.
• MySQL engine-level correctness (transactions, ACID properties) — assumed reliable; the team tests its own 
schema constraints (e.g. the duplicate-attendance unique constraint, SAM-F-013) but not MySQL itself.
• Full-scale load/stress testing against SAM-NF-001 (3-second response) and SAM-NF-007 (multiple 
simultaneous users) — flagged for a dedicated performance-testing pass once a deployable build exists (see 
Section 13.1).
• Cross-browser pixel-level UI testing — basic checks on Chrome only for this phase, consistent with SAM-NF-
003; full cross-browser testing is a stretch goal, not a Phase-3 commitment.

5. Test Approach / Strategy
Levels
• Unit tests (module-level) — one module's logic in isolation, e.g. the attendance-percentage calculation 
formula (TC-Calc-01).
• Integration tests — two or more modules working together, e.g. the Attendance Module checking the 
Student Module's enrolment list before allowing a mark.
• System tests (end-to-end) — a realistic full flow a real user would perform, login through to the final result.
Types
• Functional testing — the 20 functional requirements (SAM-F-001 to SAM-F-020), traced in Section 13.
• Security testing — the 5 security requirements (SAM-SEC-001 to SAM-SEC-005), covered wherever a use case 
touches role-based access or data isolation (see Section 5.1).
• Regression testing — informal for this phase (re-running affected test cases after a fix); a formal regression 
suite is planned once the codebase and CI pipeline (Section 6) are in place.
• Performance testing — limited to a single spot check (TC-Perf-01, see Section 13.1) against SAM-NF-001; full 
performance testing is out of scope per Section 4.
Entry criteria: the relevant module has a working build deployed to the test environment; test data (sample 
students, faculty, subjects, classes) has been seeded; the SRS requirement being tested has not changed since this 
test plan was written.
Exit criteria: all High-priority functional requirement test cases pass; all five SAM-SEC test cases pass with no 
exceptions (security requirements are treated as non-negotiable per the SRS's acceptance criteria, Section 6.2); 
any Medium-priority failures are logged as known issues with a plan to fix before final submission.
5.1 Security Validation
• Verify role-based access cannot be bypassed by direct URL/request manipulation (SAM-SEC-002, TC-SEC-02).
• Verify a student cannot access another student's data by altering a student ID in a request (SAM-SEC-004, TC-
SEC-04).
• Verify passwords are never stored or transmitted in plain text (SAM-SEC-003, TC-SEC-03) — to be checked 
once the authentication module is built, via direct database inspection.
• Verify administrative actions are recorded in an audit trail that cannot be edited or deleted through the 
normal UI (SAM-SEC-005, TC-SEC-05) — see UC-05 in Section 13.
• No formal penetration testing or fuzzing is planned for this phase, unlike the ATM sample reference; this is 
flagged as a gap to revisit if time permits before final submission.

12. Suspension and Resumption Criteria
Suspend testing if:
• The test environment (Section 6) is unavailable for an extended period (e.g. a team member's local setup 
breaks and no shared environment exists yet).
• A build is too unstable to execute a meaningful share of planned test cases for a given use case.
• A design gap noted in Section 13.1 blocks a specific use case's tests entirely (e.g. the attendance schema's 
session/slot gap for UC-01).
Resume testing if:
• The blocking issue is resolved (environment restored, build stabilised, or design decision made).
• The affected test cases have been reviewed and updated if the underlying requirement changed.

13.1 Open Items Raised While Validating Traceability
Checking this traceability against the SRS surfaced a few gaps the SRS does not resolve on its own. The team is 
listing them here rather than quietly picking an answer, since these affect the design phase:
• Same-subject, multiple-sessions-per-day: the attendance schema behind SAM-F-012 (student, subject, date) 
cannot distinguish a lecture session from a lab session on the same day for the same subject (relevant to TC-
Att-03). Needs a session/slot field added to the design before implementation, or a team decision that this is 
out of scope.

• Student record deletion: SRS Section 4.2 (SAM-F-004 to SAM-F-006) specifies add/update/search but not 
delete. The team proposes deactivation instead of hard delete, to avoid orphaning historical attendance 
records, but this should be confirmed with the course coordinator or treated as a team design decision 
documented in Phase-2.
• Audit logging of denied/failed actions: SAM-SEC-005 (TC-SEC-05) says "important attendance modifications 
and administrative actions" should be logged — it is not explicit whether a denied unauthorized attempt 
counts. The team leans towards logging these too since they are security-relevant, but is flagging this for 
team agreement.
• Report generation performance: SAM-NF-001 (TC-Perf-01) cannot be measured until a build exists to time 
against a realistically sized dataset; this is a placeholder to run once implementation exists.
• Default sort order for attendance history: SAM-F-016 (TC-View-01) does not specify newest-first vs oldest-
first; the team has suggested newest-first as more useful but this is a minor UI decision, not a blocker.
None of these block moving forward — they are the kind of small ambiguities that show up once a team actually 
checks a requirements document against real test scenarios, and the team would rather resolve them now than 
during the demo.

14. Test Metrics and Reporting
Metrics to be collected (once execution begins)
• % of test cases executed, against the 32 requirements tracked in the SRS's RTM (SRS Section 8)
• % passed / failed, broken down by use case
• Defect density (defects per module, e.g. Attendance Module vs Report Module)
• Requirement coverage — every SAM-F, SAM-NF, and SAM-SEC ID mapped to at least one executed test case, 
verifying that the SRS's RTM holds up under actual execution
Reporting
A test summary report will be produced after execution, before final Jackfruit submission, summarising pass/fail 
counts per use case and listing any open defects carried forward. No automated dashboard is planned for this 
phase; tracking will be manual via a shared spreadsheet or GitHub Project board.

Conclusion
This test plan sets the testing strategy, environment, schedule, and responsibilities for the Student Attendance 
Management System's seven use cases, across Unit, Integration, System, and dedicated Security testing levels, 
directly traceable to the 20 functional, 7 non-functional, and 5 security requirements specified in the Phase-1 SRS. 
It follows the department's 15-section Software Test Plan template structure, including that template's 
lightweight treatment of Section 13: rather than duplicating the SRS's own Requirements Traceability Matrix 
(Section 8), Section 13 here summarises it at the use-case level and points back to the SRS for full detail.
Five open design questions surfaced while validating that traceability are tracked in Section 13.1 and will be 
carried forward into the Phase-2 planning and design discussions, rather than being silently resolved by whoever 
happened to notice them.
