1. Introduction
1.1 Purpose
This document specifies the architecture and design of the Student Attendance Management System (SAMS). It turns 
the requirements of the SRS (v1.0) into a concrete structure of components, data, interfaces, and behaviour that the 
team will implement in Python/Django with MySQL, and that the test cases of the Software Test Plan (v1.0) will verify.
1.2 Scope
The design covers every SAMS service defined in the SRS: user authentication with role-based access; student, faculty, 
and subject management; attendance marking, modification, and duplicate prevention; attendance percentage 
calculation and low-attendance alerts; attendance history; student-wise, subject-wise, and class-wise reports; and 
audit logging of administrative actions. Payroll, examination evaluation, fee management, and other non-attendance 
activities remain out of scope, as in the SRS.
1.3 Audience
Developers, QA engineers, security reviewers, project guides and instructors, and future maintenance teams.

3. Architecture
3.1 Goals and Constraints
Goals
• Integrity of attendance data: no duplicate records and no unauthorised or untraceable changes (SAM-F-013, 
SO-02).
• Security: authentication before access, strict role separation, student data isolation, hashed passwords, and an 
audit trail (SAM-SEC-001 to SAM-SEC-005).
• Reliability: at least 99% availability during academic working hours, with regular backup and recovery (SAM-
NF-002, SAM-NF-005).
• Performance: 90% of normal requests complete within 3 seconds, with multiple simultaneous users supported 
(SAM-NF-001, SAM-NF-007).
• Maintainability: new features can be added without major changes to existing modules (SAM-NF-006).
Constraints
• Python 3 with Django and MySQL 8.0 are fixed for the project (SRS Sections 2.1 and 2.5).
• Passwords use a one-way hashing algorithm; plaintext storage is prohibited (SAM-SEC-003).
• All client–server communication uses HTTPS (SRS Section 3.4).
• The institution's attendance rules apply, including a configurable minimum-attendance threshold (SAM-F-017).
• The course guidelines mandate Git and GitHub with code reviews, a CI/CD pipeline, Docker, static analysis 
(SonarQube or similar), security validation, and unit tests reported with code and branch coverage. Section 3.6 
records the resulting toolchain.
• Development and testing run on team members' own laptops; Chrome is the primary test browser (STP Section 
6).

3.5 Chosen Architecture Pattern and Rationale
SAMS uses a layered, monolithic architecture (Presentation → Application → Data Access → Persistence), 
implemented with Django's MVT structure. Each functional area is a separate Django app with its own models, views, 
and templates, which keeps responsibilities separated and supports the maintainability goal (SAM-NF-006).
Why layered: clear separation of concerns; maps directly onto Django; easy for a four-person team to divide by 
module; simple to test with unit tests per module and integration tests across modules.
Why not microservices: rejected as overly complex for an institution-level class project. Separate deployments, inter-
service networking, and distributed data would add operational cost without a scale requirement to justify it. A well-
modularised monolith can still be split later along module lines (ADR-001).

3.9 Security Architecture
Security controls are layered. Transport is protected by HTTPS; every request passes through the Authentication & 
Access Control component before reaching any business module (default-deny); object-level checks bind students to 
their own records; passwords are hashed by Django; and sensitive actions, including denied attempts, are written to 
an append-only audit log in the same transaction as the action. Security validation is also part of the build: the GitHub 
Actions workflow runs the SonarCloud scan, a Bandit security scan, and the per-role access tests on every push and 
pull request.

4. Design
4.1 Design Overview
SAMS is built as a set of Django apps that mirror the modules in the SRS RTM: auth, students, faculty, subjects, 
attendance, reports, and audit. Each app has the same internal structure: models (data), services (business rules such 
as percentage calculation and duplicate handling), views (request handling and permission checks), and templates 
(presentation). Keeping business rules in services means they can be unit-tested without a browser.
Design rules:
• Every view is protected by a role check unless explicitly marked public (the login page only).
• All attendance writes happen inside one database transaction: every row is saved, or none.
• Business logic lives in service functions, never in templates.
• Administrative and security-relevant actions always call the Audit Module, inside the same transaction as the 
change.
4.1.1 Data Model
Figure 4.1 shows the persistent entities. The college takes attendance by time, in one-hour slots. A subject has several 
classes, some of them labs, and a lab and a theory class of the same subject can fall on the same day. Each hour is 
marked against a TimeSlot (a defined one-hour period such as 09:00–10:00), and Attendance is unique on (student, 
subject, date, time slot). A one-hour theory class is one entry per student; a two-hour lab occupies two consecutive 
slots and is stored as two entries, so it counts as two classes. Lab and theory classes of a subject are one subject and 
count together in one percentage. SAM-F-012 and SAM-F-013 in the SRS name only student, subject, and date; adding 
the time slot refines them, and the SRS wording is to be updated (ADR-004).
Figure 4.1 — SAMS entity-relationship diagram
Attendance percentage. For a student and subject: percentage = (classes marked PRESENT ÷ total classes recorded) × 
100, rounded to two decimals. Each one-hour time slot is one class, so a one-hour theory class counts as 1 and a two-
hour lab counts as 2; all of a subject's classes, theory and lab, count together in this one figure. If no classes have been 
recorded yet, the percentage is shown as 'No data' rather than 0%, and no warning is raised.
Low-attendance rule. A warning is produced when a subject's percentage is below the threshold stored in 

Page 13
SystemSetting. The SRS requires the threshold to be configurable but does not fix a value, so the design ships with a 
default of 75%, which the Administrator can change.
Login lockout. The lockout package keeps its failed-login counters in its own tables, outside the SAMS domain model 
in Figure 4.1. The limits (5 failures, 15 minutes) are configurable defaults, since the SRS does not fix them.

4.3 API Design
SAMS is a server-rendered web application (ADR-006), so its interfaces are HTTP endpoints handled by Django views. 
Requests are HTML form submissions carrying a CSRF token; responses are rendered pages or redirects, with the 
HTTP status codes listed below. All endpoints require HTTPS and an authenticated session unless marked Public. The 
Authentication and Attendance components are defined in full; the remaining endpoints follow in summary form. An 
ABI definition does not apply: SAMS is interpreted Python with no compiled binary interfaces between components, 
so its stable interfaces are the HTTP endpoints below and the database schema (Section 4.1.1).

4.4 Error Handling, Logging, and Monitoring
Error handling
• Standard, user-friendly messages shown inline on forms; custom 403, 404, and 500 pages; a clear message when 
the database or network is unavailable rather than failing silently (SRS Section 3.4).
• Server-side validation of every input (status values, dates not in the future, defined time slots, student belongs 
to the selected class); client-side checks are never relied on alone.

Page 19
• A duplicate attendance record is caught by the database unique constraint and reported as a duplicate, not as a 
server error.
• Multi-row attendance saves use one transaction, so a failure part-way leaves no partial data.
Logging
• Application log (rotating files): errors, warnings, and failed requests with a timestamp and request id.
• Audit log (append-only database table): user, action, target, outcome (SUCCESS, DENIED, or FAILED), and 
timestamp for administrative actions, attendance modifications, failed logins, and denied access attempts. The 
entry is written in the same transaction as the change it records.
• No passwords, session tokens, or full personal records are written to any log.
Monitoring
• Availability (SAM-NF-002): an uptime check on the login page during academic hours.
• Response time (SAM-NF-001): requests slower than 3 seconds are logged.
• Failure indicators: rate of failed logins, 403s, and 500s; backup job success or failure; database disk usage; 
GitHub Actions workflow and SonarCloud quality-gate status.
4.5 UX Design
• One login page for all roles, followed by a role-specific dashboard (Student: percentages and alerts; Faculty: 
assigned subjects and quick marking; Administrator: management menu).
• Attendance-marking sheet: pick the date and one or more time slots (a two-hour lab uses two consecutive slots), 
then one row per student with a Present/Absent toggle, a 'mark all present' shortcut, and a clear save 
confirmation, so a class can be marked in under a minute. The same marks are saved for every selected slot, and 
a single hour can be corrected afterwards through the edit endpoint.
• Low-attendance subjects carry a warning badge with text, not colour alone, for accessibility.
• Responsive Bootstrap layout on desktop, tablet, and phone; consistent navigation and primary buttons; readable 
font sizes and sufficient contrast.
• Reports in clear tables with filters (type, subject or class, date range) and visible Print and Download buttons.
• Inline validation messages; deactivation and other sensitive actions ask for confirmation.
