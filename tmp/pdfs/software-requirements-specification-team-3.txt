1. Introduction
1.1 Purpose
This document is the Software Requirements Specification (SRS) for the Student Attendance Management System 
(SAMS), developed by Team 3 as part of the UE24CS341A Software Engineering mini-project. It defines the functional 
and non-functional requirements, system interfaces, features, quality attributes, and verification criteria of the 
system. The document serves as the reference baseline for developers, faculty members, administrators, students, 
and project evaluators through the requirements, design, implementation, and testing phases of the project.
1.2 Scope
The Student Attendance Management System automates the recording, management, monitoring, and reporting of 
student attendance, replacing manual attendance registers with a centralized digital platform. Faculty members mark 
attendance for their assigned classes, students view their own attendance records, and administrators manage 
students, faculty, subjects, and system-wide attendance data.
Core capabilities include user authentication with role-based access, attendance recording and correction, automatic 
attendance-percentage calculation, attendance history and reporting, and low-attendance alerts.
Out of scope: payroll management, examination evaluation, fee management, and any other non-academic 
administrative activity not directly related to attendance tracking.
1.3 Intended Audience
• Developers, who need to understand and implement the system requirements.
• Faculty members, who will record and monitor student attendance.
• Students, who will view their attendance status and history.
• Administrators, who manage users, subjects, classes, and system data.
• QA/test engineers, who verify and validate system functionality against this SRS.
• Project guides and evaluators, who assess requirement coverage and implementation quality.
The remainder of this document is organized following the standard SRS structure: overall system description, 
external interfaces, detailed functional and non-functional requirements, quality attributes, use-case diagrams, and 
the requirements traceability matrix.

2. Overall Description
2.1 Product Perspective
The Student Attendance Management System (SAMS) is a new, self-contained web-based application; it is not a 
follow-on to an existing institutional system. It replaces manual, register-based attendance tracking with a centralized 
system comprising a browser-based user interface, an application server, and a relational database.
The system uses Python with the Django web framework for the application layer and MySQL for relational 
persistence. Django was selected for its built-in authentication module, role-based authorization support, and ORM 
capabilities, which streamline entity mapping for students, faculty, courses, and attendance records. MySQL provides 
standard relational integrity, acid-compliant transactions, and native foreign-key constraints to prevent data 
duplication.
Faculty members record attendance for their assigned subjects, students view their own attendance status, and 
administrators manage students, faculty, subjects, classes, and attendance records. A high-level view of the major 
components and their interconnections is provided as a structural note: the browser-based client communicates over 
HTTPS with the Django application server, which in turn performs all reads and writes against the MySQL database; no 
other external system integration is required for the current scope.
2.2 Product Functions
The major functions of the system, summarized at a high level (details are in Section 4), are:
• User Authentication: secure login with role-based access for Admin, Faculty, and Student.
• Student Management: add, update, search, and view student records.
• Faculty and Subject Management: maintain faculty profiles, create subjects, and assign subjects to faculty.
• Attendance Recording: mark students Present/Absent per class and subject, with duplicate-entry prevention.
• Attendance Modification: authorized correction of previously recorded attendance.
• Attendance Monitoring: automatic percentage calculation and history viewing.
• Attendance Reports: student-wise, subject-wise, and class-wise reports, downloadable/printable.
• Low-Attendance Alerts: automatic warnings when a student's attendance falls below the configured threshold.
• Dashboards: role-specific dashboards for Admin, Faculty, and Student.
2.3 User Classes and Characteristics
Student
• Logs in using valid credentials issued by the institution.
• Views personal attendance records, subject-wise percentage, and history.
• Receives low-attendance warnings.
• Requires only basic computer or smartphone familiarity; this is the most frequent but least privileged user class.
Faculty
• Logs in securely and views assigned classes and subjects.
• Marks and corrects attendance, and generates attendance reports for their subjects.
• Requires basic familiarity with the institution's attendance process; moderate frequency of use, moderate 
privilege.

Page 7
Administrator
• Has full administrative access: manages student and faculty accounts, departments, classes, and subjects.
• Assigns subjects to faculty and views consolidated, institution-wide attendance reports.
• Least frequent user class but highest privilege level; most important for data integrity and system configuration.
2.4 Operating Environment
• Client: desktop, laptop, tablet, or smartphone with a modern web browser (Chrome, Edge, Firefox).
• Frontend: HTML, CSS, JavaScript, with Bootstrap for responsive layout.
• Backend: Python 3 with the Django web framework.
• Database: MySQL (relational).
• Server operating system: Linux (Ubuntu), compatible with Windows/macOS for local development.
• Network: institutional LAN or the internet, secured with HTTPS.
2.5 Design and Implementation Constraints
• The backend framework and database are fixed as Django and MySQL for this project (Section 2.1); no alternate 
stack will be introduced mid-project.
• Only authenticated users may access protected system functions, and access must match the user's assigned 
role.
• Only authorized faculty or administrators may modify attendance records once submitted.
• Passwords must be stored using a one-way hashing algorithm (Django's default PBKDF2/Argon2 password 
hasher); plaintext storage is prohibited.
• Regular database backups must be scheduled to prevent loss of attendance records.
• The system must follow the attendance rules and policies defined by the institution (e.g., minimum attendance 
percentage thresholds).
2.6 Assumptions and Dependencies
• It is assumed that all students and faculty are issued institutional credentials prior to system rollout; the system 
does not perform its own identity verification against external ID documents.
• The system depends on continuous availability of the MySQL database and the underlying network for normal 
operation; extended outages will degrade functionality.
• It is assumed that class timetables and subject-to-semester mappings are supplied by the administrator and are 
accurate at the time attendance is recorded.
• The project depends on Django's built-in authentication and ORM libraries, which are assumed to remain stable 
for the duration of development.

3. External Interface Requirements
3.1 User Interfaces
The system provides a simple, role-aware web interface:
• A single login page shared by students, faculty, and administrators, differentiated by role after authentication.
• A role-specific dashboard shown immediately after login (Section 2.2).
• Forms for entering and updating student, faculty, subject, and attendance details, with inline validation.
• An attendance-marking interface presenting each enrolled student with a Present/Absent toggle.
• Attendance-percentage and report views with clear tabular layouts.
• Consistent navigation menus, clear primary-action buttons, and legible error messages.
• A responsive layout usable on desktop, tablet, and smartphone screens.
3.2 Hardware Interfaces
The system requires no specialized hardware and runs on standard computing devices.
• Keyboard and mouse, or touchscreen, for data entry and navigation.
• A standard display for viewing the application.
• A printer, optionally, for physical copies of attendance reports.
• Standard server hardware (or a cloud virtual machine) to host the Django application and MySQL database.
3.3 Software Interfaces
• Database: MySQL, accessed through the Django ORM, for storing student, faculty, subject, and attendance data.
• Backend framework: Django (Python 3), handling request routing, business logic, and template rendering.
• Web browser: Google Chrome, Microsoft Edge, or Mozilla Firefox (current stable releases).
• Authentication module: Django's built-in authentication system, extended with role-based permission checks for 
Admin, Faculty, and Student.
• Reporting module: a Django-based reporting component that queries attendance data and renders it as on-
screen tables and downloadable/printable documents.
3.4 Communications Interfaces
• All communication between the browser, application server, and database occurs over the institutional network 
or the internet.
• HTTPS (TLS) is used to protect all data transmitted between the client and the server.
• The system displays clear, user-facing error messages when the network or server is unavailable, rather than 
failing silently.
• Database connections are restricted to the application server and secured to prevent unauthorized direct 
access.

6. Quality Attributes & Acceptance Tests
6.1 Quality Attributes
The Student Attendance Management System shall exhibit the following quality attributes:
• Usability: the system shall be simple and easy to use for students, faculty, and administrators.
• Performance: the system shall respond quickly to user requests (Section 5, SAM-NF-001).
• Reliability: attendance records shall be stored accurately without data loss.
• Security: only authorized users shall be able to access or modify attendance information.
• Maintainability: the system shall be easy to update and extend as new features are required.
• Scalability: the system shall support an increasing number of students and attendance records without 
significant degradation.
6.2 Acceptance Criteria
A build is considered acceptance-ready when: all High-priority functional requirements (Section 4) are implemented 
and pass their reference test cases; no critical non-functional requirement (Section 5) fails; all five security 
requirements (Section 5.1.2) pass; and the Requirements Traceability Matrix (Section 8) shows every requirement 
mapped to a design module and test case with no unresolved gaps.
6.3 Acceptance Test Cases
The following test suites shall be used to verify the system prior to final submission:
Test Suite Purpose
Authentication Test Verify login, logout, and role-based access.
Student Management Test Verify adding, updating, searching, and viewing students.
Attendance Test Verify marking, updating, and storing attendance.
Attendance Calculation Test Verify correct attendance percentage calculation.
Report Test Verify generation and downloading of attendance reports.
Performance Test Verify that the system responds within the specified time.
Security Test Verify authentication, authorization, password protection, and 
data access controls.

7. System Models and Diagrams
7.1 Actors
The Student Attendance Management System defines the following actors:
• Student: a user who views their own attendance records, percentage, and history.
• Faculty: a user who records and modifies attendance for their assigned classes and subjects, and generates 
reports.
• Administrator: a user who manages student, faculty, and subject data, assigns subjects to faculty, configures the 
attendance threshold, and views consolidated reports.
• Audit Module: a system-internal actor that receives and stores the log of sensitive administrative actions 
(Section 5.1.2, SAM-SEC-005).
7.2 Use Cases
The primary use cases, grouped by actor, are summarized below and shown in the two use-case diagrams that follow 
(Section 7.3). Several use cases include a shared sub-use-case, shown as a separate oval connected by an «include» 
relationship: for example, Log In / Authenticate includes both Authenticate Credentials and Validate User Role, and 
Mark Attendance includes Select Class and Subject and Save Attendance Record.
• Student: Log In / Authenticate, View Attendance History, View Attendance Percentage, Receive Low-Attendance 
Alert.
• Faculty: Log In / Authenticate, View Assigned Subjects, Select Class and Subject, Mark Attendance, Modify 
Attendance Record, Generate Reports.
• Administrator: Manage Student Records, Manage Faculty Records, Manage Subjects and Classes, Assign Subjects 
to Faculty, Manage User Access, View Consolidated Attendance Reports, Configure Attendance Threshold, 
Manage Database Backup.

7.4 Use-Case Descriptions
UC-01: Mark Attendance
Actor: Faculty. Precondition: Faculty is authenticated and has at least one assigned class/subject. Main flow: (1) 
Faculty selects class and subject (includes UC-02); (2) system displays the enrolled student list; (3) Faculty marks each 
student Present or Absent; (4) system stores the record with student ID, subject, date, and status, rejecting duplicates 
for the same student/subject/date (SAM-F-013). Postcondition: attendance for the session is recorded and available 
for percentage calculation.
UC-02: Select Class and Subject
Actor: Faculty. Included by UC-01. Main flow: Faculty selects one of their assigned classes and subjects from a list 
scoped to their account; the system validates the selection before proceeding.
UC-03: View Attendance Percentage
Actor: Student. Precondition: Student is authenticated. Main flow: Student requests their attendance summary; the 
system calculates the percentage per subject from stored records (SAM-F-015) and displays it, along with a low-
attendance warning if the percentage is below the configured threshold (SAM-F-017).

Page 19
UC-04: Manage User Access
Actor: Administrator. Main flow: Administrator creates, updates, or deactivates a student or faculty account and 
assigns its role. This action includes UC-05 (Log Administrative Action) so that the change is auditable.
UC-05: Log Administrative Action
Actor: Audit Module (system). Triggered by: UC-04 and other record-modifying or access-control administrator 
actions (Manage Student Records, Assign Subjects to Faculty, Configure Attendance Threshold, Manage Database 
Backup). Main flow: the system records the acting user, the action taken, and a timestamp to the audit log (SAM-
SEC-005).
UC-06: Generate Reports
Actor: Faculty or Administrator. Precondition: user is authenticated and has report-viewing permission for the 
requested scope. Main flow: user selects the report type (student-wise, subject-wise, or class-wise) and a date range 
(includes Select Report Type and Range); the system compiles the report from stored attendance records (SAM-F-018 
to SAM-F-020) and returns it in an on-screen, printable, or downloadable format.
UC-07: View Attendance History
Actor: Student or Faculty. Precondition: user is authenticated. Main flow: user requests attendance history for a 
subject or class; the system retrieves matching records and displays them chronologically. Students see only their 
own records (SAM-SEC-004); faculty see records for classes they are assigned to.

9. Conclusion
This document has specified the functional requirements (20, Section 4), non-functional requirements (7, Section 5), 
security objectives and requirements (2 and 5 respectively, Section 5.1), quality attributes and acceptance criteria 
(Section 6), use-case models (Section 7), and full requirements traceability (Section 8) for the Student Attendance 
Management System.
The team has committed to a Python/Django backend with a MySQL database (Section 2.1). The requirement set 
establishes a three-role access architecture (Student, Faculty, and Administrator) with attendance recording, 
calculation, and reporting as core functionalities. This SRS forms the baseline against which the subsequent project 
plan, test plan, and implementation deliverables will be developed and verified.
